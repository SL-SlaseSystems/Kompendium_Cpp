# C++23

C++23 jest bazą tego kompendium i bieżącym opublikowanym standardem. Język dodał m.in. explicit object parameter, `if consteval`, rozszerzenia `constexpr`, portable assumptions przez `[[assume]]` oraz dalsze ulepszenia lambd i dedukcji. Biblioteka obejmuje między innymi `std::expected`, `std::print`, `std::stacktrace`, `std::mdspan`, ranges improvements, monadic operations dla optional i expected oraz kolejne utilities.

Nie wszystkie funkcje C++23 są dostępne w każdej bibliotece pracującej z kompilatorem akceptującym `-std=c++23`. Dlatego przykład wykorzystuje mechanizmy o szerokim wsparciu i compile-time detekcję:

~~~cpp
#include <cassert>
#include <optional>
#include <version>

int main() {
    std::optional<int> value = 21;
#if defined(__cpp_lib_optional) && __cpp_lib_optional >= 202110L
    const auto doubled = value.transform([](int number) { return number * 2; });
    assert(doubled == 42);
#else
    assert(value && *value * 2 == 42);
#endif
}
~~~

Feature-test macro należy porównywać z wartością odpowiadającą konkretnej rewizji, nie tylko sprawdzać obecność. Nagłówek `<version>` zbiera wiele makr bibliotecznych, ale czasem właściwy nagłówek funkcji jest praktyczniejszy.

`std::expected` daje jawny typ błędu, `std::print` prostsze wyjście formatowane, a `mdspan` wielowymiarowy niewłaścicielski widok z konfigurowalnym layoutem. Każdy z tych typów ma szczegółowe kontrakty i nie jest tylko składniowym skrótem.

## Jak to działa krok po kroku

Przyjmij, że parser zwraca liczbę albo wyjaśnienie niepowodzenia. `expected<T, E>` przechowuje jeden z tych stanów. `transform` przelicza poprawny wynik zwykłą funkcją, a `and_then` łączy go z kolejną operacją, która również może zwrócić `expected`. Jeżeli pojawi się błąd, następny etap obliczający wartość nie zostaje wywołany. To porządkowanie przepływu błędów, a nie automatyczne wykonanie równoległe ani przechwytywanie wszystkich wyjątków.

Przy modernizacji pojedynczego fragmentu najpierw zapisz dotychczasowy kontrakt błędów i własności, następnie wybierz nowy mechanizm, a na końcu sprawdź jego dostępność. `optional::transform` z przykładu upraszcza przeliczenie wartości, ale nie zmienia pustego stanu w domyślną liczbę. Fallback powinien zachowywać tę samą semantykę, a nie tylko produkować ten sam wynik dla jednego testu.

## Pogłębienie mechanizmu

Explicit object parameter pozwala zapisać parametr obiektu jawnie i w odpowiednim szablonie dedukować jego cv-kwalifikację oraz kategorię wartości. Może ograniczać powielanie metod dla `&`, `const&` i `&&`. Nadal trzeba zdecydować, czy wynik ma być kopią czy referencją oraz czy wolno zwrócić widok do tymczasowego obiektu. Mniej przeciążeń nie usuwa problemu dangling.

`if consteval` wybiera ścieżkę zależnie od tego, czy dana ewaluacja zachodzi w wymaganym kontekście stałym. To nie to samo co `if constexpr`, którego warunek opisuje wybór odrzucanej gałęzi podczas instancjacji. W gałęzi runtime można użyć wydajnej implementacji niedostępnej w constant evaluation, a w gałęzi compile-time obliczyć ten sam wynik inną metodą. Dwie ścieżki powinny realizować wspólny kontrakt.

`[[assume(condition)]]` jest deklaracją założenia dla optymalizatora, a nie kontrolą danych wejściowych. Fałszywe założenie może prowadzić do UB. Nie używaj go jako zamiennika `if`, wyjątku ani walidacji parsera. Podobnie `mdspan` opisuje mapowanie indeksów do pamięci, lecz nie przejmuje własności ani nie dowodzi poprawności każdego indeksu.

## Drugi przykład

~~~cpp
#include <cassert>

// Kontrakt dydaktyczny: n <= 1000.
constexpr unsigned long triangular(unsigned long n) {
    if consteval {
        return n * (n + 1ul) / 2ul;
    } else {
        unsigned long result = 0;
        for (unsigned long i = 1; i <= n; ++i) result += i;
        return result;
    }
}

int main() {
    static_assert(triangular(10) == 55);
    unsigned long input = 10;
    const unsigned long result = triangular(input);
    assert(result == 55);
}
~~~

`static_assert` wymaga stałego obliczenia, więc używany jest wzór. Zwykłe wywołanie realizuje ścieżkę runtime, nawet jeśli optimizer później potrafi uprościć pętlę do stałej. Optymalizacja kodu maszynowego nie jest definicją kontekstu constant evaluation. Typ `unsigned long` zapewnia co najmniej 32 bity, więc iloczyn dla podanego limitu jest reprezentowalny także na implementacji z 16-bitowym `unsigned int`. Ograniczenie wejścia chroni obie implementacje przed innymi zachowaniami wynikającymi z arytmetyki modulo i przepełnienia licznika pętli.

## Porównanie i decyzje

`expected` jest przydatne, gdy typ błędu i konieczność obsłużenia wyniku mają być widoczne w sygnaturze. Wyjątki nadal mogą lepiej przenosić awarię przez wiele warstw. `print` upraszcza wyjście, ale nie stanowi systemu logowania z rotacją, synchronizacją i kontrolą prywatności. `mdspan` pomaga reprezentować istniejący bufor wielowymiarowy; `vector` nadal może być jego właścicielem.

C++23 jest zestawem zmian o różnej dojrzałości implementacji. Gdy konkretna funkcja jest ważna dla publicznego API, przetestuj najstarszą obsługiwaną konfigurację, a nie jedynie najnowszy komputer autora. Wdrożenie kilku przydatnych narzędzi nie wymaga przepisania całego programu na każdą nową konstrukcję.

## Ćwiczenie z odpowiedzią

Czy zastąpienie `if consteval` przez `if constexpr (std::is_constant_evaluated())` zachowa zamysł? Nie: warunek `if constexpr` sam podlega stałej ewaluacji, przez co takie użycie nie rozróżnia zwykłego wykonania w oczekiwany sposób. Zastanów się też, czy funkcja przekazana do `expected::transform` może rzucić wyjątek. Może, jeśli jej własna implementacja go rzuca; wrapper wyniku nie zamienia go automatycznie w `E`.
