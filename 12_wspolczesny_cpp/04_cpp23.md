# C++23

C++23 jest bazą tego kompendium i bieżącym opublikowanym standardem. Język dodał m.in. explicit object parameter, `if consteval`, rozszerzenia `constexpr`, portable assumptions przez `[[assume]]` oraz dalsze ulepszenia lambd i dedukcji. Biblioteka obejmuje między innymi `std::expected`, `std::print`, `std::stacktrace`, `std::mdspan`, ranges improvements, monadic operations dla optional i expected oraz kolejne utilities.

Nie wszystkie funkcje C++23 są dostępne w każdej bibliotece pracującej z kompilatorem akceptującym `-std=c++23`. Dlatego przykład wykorzystuje mechanizmy o szerokim wsparciu i compile-time detekcję:

~~~cpp
#include <cassert>
#include <optional>
#include <version>

int main() {
    std::optional<int> value = 21;
#if defined(__cpp_lib_optional) && __cpp_lib_optional >= 202110L
    const auto doubled = value.transform([](int number) { return number * 2; });
    assert(doubled == 42);
#else
    assert(value && *value * 2 == 42);
#endif
}
~~~

Feature-test macro należy porównywać z wartością odpowiadającą konkretnej rewizji, nie tylko sprawdzać obecność. Nagłówek `<version>` zbiera wiele makr bibliotecznych, ale czasem właściwy nagłówek funkcji jest praktyczniejszy.

`std::expected` daje jawny typ błędu, `std::print` prostsze wyjście formatowane, a `mdspan` wielowymiarowy niewłaścicielski widok z konfigurowalnym layoutem. Każdy z tych typów ma szczegółowe kontrakty i nie jest tylko składniowym skrótem.

## Jak to działa krok po kroku

1. **Zapisz kontrakt.** Określ, jakie wartości i typy wchodzą do mechanizmu „C++23”, jaki stan jest poprawny oraz co wywołujący może obserwować po sukcesie i porażce.
2. **Prześledź fazę języka.** Rozpisz identyfikację wymaganej funkcji, sprawdzenie feature-test macro, wybór implementacji i weryfikację na wszystkich wspieranych toolchainach. Pozwala to wskazać, czy decyzja zapada w preprocessing, podczas kompilacji, linkowania czy dopiero w runtime.
3. **Ustal granice odpowiedzialności.** Dla tego zagadnienia trzeba oddziel wersję języka ustawioną flagą od faktycznej implementacji funkcji i dostępności odpowiedniego komponentu biblioteki standardowej. Szczególnie ważne są ownership, lifetime i miejsce, w którym obowiązuje inwariant.
4. **Zbierz dowód.** Sprawdź wartość makra funkcji, wynik kompilacji minimalnego przykładu, status implementacji i test na najstarszym wspieranym narzędziu. Jeden poprawny output nie wystarcza, jeśli program mógł wcześniej wykonać undefined behavior albo zależy od niejawnej konfiguracji.

Model dla tej części kompendium jest następujący: Edycje standardu dodają język i bibliotekę, lecz ich obecność w dokumencie nie oznacza kompletnego wsparcia toolchainu. Kod produkcyjny potrzebuje macierzy kompilator–biblioteka–platforma oraz polityki fallbacku. W praktyce warto narysować małą oś czasu obiektu lub artefaktu: utworzenie, wszystkie miejsca przekazania, moment ostatniego legalnego użycia i zakończenie. Taki zapis często ujawnia błąd wcześniej niż analiza samej składni.

## Pogłębienie mechanizmu

- C++23 rozwija `expected`, ranges, formatowanie, utility types i constexpr. Dostępność funkcji bibliotecznej zależy nie tylko od frontendu kompilatora, lecz również od wersji libstdc++, libc++ albo biblioteki MSVC.

Pojęcia wymienione wyżej współdziałają, lecz nie powinny być zlewane w jedną regułę. Dla „C++23” osobno sprawdź poprawność programu wobec standardu, wymagania używanego API oraz koszt konkretnej implementacji. Dzięki temu optymalizacja nie ukryje naruszenia kontraktu, a szczegół jednego kompilatora nie zostanie przedstawiony jako przenośna gwarancja C++.

## Drugi przykład

Poniższy scenariusz jest przykładem diagnostycznym. Uzupełnia kompilowalny kod z początku rozdziału o przypadek graniczny i sposób weryfikacji założenia.

~~~text
Temat: C++23
Przypadek podstawowy: minimalne poprawne dane i jeden właściciel zasobu
Zmiana kontrolna: pusty zakres, przeniesiony obiekt, wyjątek albo konkurencyjny dostęp
Pytanie: który kontrakt przestaje obowiązywać i w którym momencie?
Dowód: diagnostyka kompilatora + sanitizer/test + stan przed i po operacji
Decyzja: wybór prostszego wariantu, który jawnie koduje ownership i lifetime
~~~

Najpierw uruchom przypadek podstawowy, potem zmień dokładnie jeden warunek. Jeśli problem dotyczy typów, zachowaj te same dane; jeśli lifetime, zachowaj typy i przesuń moment zniszczenia. Przy współbieżności dodaj prawdziwą synchronizację zamiast opóźnień czasowych. Taki eksperyment rozdziela przyczynę od przypadkowej zmiany layoutu, optymalizacji lub harmonogramu.

## Porównanie i decyzje

Wybierając rozwiązanie dla „C++23”, oceniaj wartość funkcji dla projektu, dojrzałość implementacji, koszt fallbacku, wpływ na ABI oraz termin wsparcia toolchainu. Wariant bardziej ogólny nie jest automatycznie lepszy: szablon może wydłużyć kompilację, polimorfizm dynamiczny może utrudnić value semantics, a współdzielona własność może ukryć cykl. Preferuj najmniejszy interfejs, który wyraża wymagany kontrakt i uniemożliwia typowe błędne stany.

Przed zatwierdzeniem API odpowiedz: kto posiada zasób, jak długo obowiązuje każdy widok, co dzieje się przy częściowym niepowodzeniu i czy zachowanie zależy od ABI lub wersji standardu? Następnie sprawdź wariant prostszy — wartość zamiast wskaźnika, RAII zamiast ręcznego cleanup, algorytm standardowy zamiast pętli albo mutex zamiast lock-free. Bardziej złożony mechanizm jest uzasadniony dopiero wtedy, gdy wymaganie lub pomiar odrzuca prostsze rozwiązanie.

## Dobre praktyki

Ustal minimalne wersje kompilatorów oraz bibliotek, a nie tylko nazwę standardu. Dodaj test konfiguracji każdej wymaganej funkcji. Fallback ma zachowywać semantykę, a nie jedynie kompilować się.
