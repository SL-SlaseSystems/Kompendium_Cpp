# C++11 i C++14

C++11 był dużą zmianą w kierunku współczesnego języka. Wprowadził move semantics, rvalue references, lambdy, `auto`, range-based for, variadic templates, `constexpr`, delegating constructors, `nullptr`, scoped enums, attributes, thread library i smart pointery. C++14 dopracował te mechanizmy, dodając m.in. generic lambdas, return type deduction, variable templates i bardziej użyteczne `constexpr`.

~~~cpp
#include <algorithm>
#include <cassert>
#include <memory>
#include <vector>

int main() {
    auto owner = std::make_unique<int>(7); // make_unique: C++14
    std::vector<int> values{1, 2, 3};
    const auto factor = *owner;
    std::transform(values.begin(), values.end(), values.begin(),
        [factor](auto value) { return value * factor; });

    assert((values == std::vector{7, 14, 21}));
}
~~~

Przykład jest sprawdzany bazowym walidatorem jako C++23, ale używa wyłącznie mechanizmów dostępnych w C++14: `make_unique`, generycznej lambdy, przechwycenia i klasycznego `std::transform`. Można go również kompilować z `-std=c++14`.

Największa zmiana stylu polegała na odejściu od ręcznego `new/delete` i makr na rzecz typów bibliotecznych, lambd, RAII i dedukcji. `nullptr` jest typowanym null pointer constant i powinien zastąpić `0`/`NULL` w przeciążonym API. `override` pozwala kompilatorowi sprawdzać wirtualne override, a `enum class` ogranicza kolizje i niejawne konwersje.

C++14 nie jest dziś rozsądnym domyślnym celem nowego kompendium, ale wiele istniejących systemów utrzymuje ten baseline. Zawsze oddzielaj „język potrafi” od „minimalny toolchain projektu potrafi”.

## Jak to działa krok po kroku

Rozpatrz modernizację obiektu posiadającego dynamiczną kolekcję. W dawnym kodzie mógł on ręcznie przydzielać tablicę, kopiować ją i zwalniać. Zastąpienie reprezentacji przez `vector` usuwa konieczność samodzielnego definiowania funkcji specjalnych. Dodane w C++11 operacje przenoszenia pozwalają przekazywać zasoby między wartościami tam, gdzie właściwy typ i kategoria wyrażenia umożliwiają ruch.

Następnie zastąp funkcję pomocniczą używaną wyłącznie w algorytmie przez lambdę. Zapis przechwycenia określa, jakie dane obiekt funkcyjny przechowuje. C++14 pozwala przechwycić obiekt z inicjalizatorem, na przykład `p = std::move(owner)`, a parametry `auto` tworzą generyczny operator wywołania. Te funkcje łączą zarządzanie własnością z lokalnym opisem operacji.

## Pogłębienie mechanizmu

`auto` nie oznacza typu dynamicznego. Kompilator ustala jeden typ na podstawie inicjalizatora. Przy deklaracji przez wartość odpadają zewnętrzne referencje i kwalifikacja `const`; zapis `auto&` lub `const auto&` zmienia sposób dedukcji i wiązania. Zwięzłość jest korzystna, gdy znaczenie pozostaje jasne, ale w publicznym interfejsie jawny typ wyniku może lepiej dokumentować kontrakt.

`nullptr` ma własny typ i rozwiązuje problem przeciążonego API, w którym zero może oznaczać zarówno liczbę, jak i pusty wskaźnik. Z kolei `enum class` ogranicza niejawne konwersje wartości wyliczeniowej do liczb. Nie są to wyłącznie udogodnienia pisania: pozwalają systemowi typów odrzucić pomylenie dwóch domen wartości.

Lambdy są obiektami. Przechwycenie przez wartość kopiuje lub inicjalizuje pole zamknięcia, a przechwycenie przez referencję zachowuje zależność od zewnętrznego czasu życia. Jeśli lambda ma przetrwać funkcję, odczyt lokalnej zmiennej przez referencję staje się niepoprawny. Przeniesienie `unique_ptr` do lambdy może natomiast przekazać jej zasób, lecz wtedy zamknięcie nie jest kopiowalne.

`constexpr` z C++14 umożliwia więcej zwykłej składni, w tym pętle w odpowiednich funkcjach. Nadal nie znaczy, że każde wywołanie odbędzie się podczas kompilacji. Obowiązek stałego obliczenia wynika z kontekstu, na przykład `static_assert` lub inicjalizacji zmiennej `constexpr`.

## Drugi przykład

~~~cpp
#include <cassert>
#include <memory>
#include <utility>

int main() {
    auto owner = std::make_unique<int>(7);
    auto operation = [resource = std::move(owner)](int value) {
        return *resource + value;
    };
    assert(!owner);
    assert(operation(35) == 42);
    auto transferred = std::move(operation);
    assert(transferred(1) == 8);
}
~~~

Ten przykład korzysta wyłącznie z mechanizmów dostępnych w C++14. Zasób przechodzi do pola lambdy, a potem do drugiego obiektu zamknięcia. Próba skopiowania `operation` nie skompiluje się, ponieważ jej pole `unique_ptr` nie ma operacji kopiowania. Nie wywołuj pierwszego zamknięcia po ruchu: jego implementacja dereferencjonuje wskaźnik, który po przeniesieniu jest pusty.

## Porównanie i decyzje

Modernizuj kod według korzyści semantycznych. Zamiana właścicielskiego wskaźnika na typ RAII usuwa klasę błędów zasobów; zamiana każdego jawnego typu na `auto` nie daje podobnej gwarancji. Dodawaj `override` tam, gdzie zamiarem jest nadpisanie wirtualnej funkcji, a `= delete` tam, gdzie operacja powinna być zabroniona. Kompilator może wtedy sprawdzić intencję.

Zachowanie starszego standardu może być wymaganiem odbiorców biblioteki. W takim przypadku sprawdzaj kod rzeczywiście w trybie C++14, a nie tylko C++23. Przejście w nowszym trybie nie dowodzi zgodności ze starszym: pojedyncze użycie structured bindings albo ranges zmienia minimalne wymagania. Historię języka warto poznawać poprzez zmiany modelu, nie zapamiętywanie samych dat.

## Ćwiczenie z odpowiedzią

Czy lambdę posiadającą `unique_ptr` można przechować w `std::function<int(int)>`? Nie w zwykłej postaci: `std::function` wymaga kopiowalnego celu. Wybierz bezpośredni typ zamknięcia, parametr szablonu albo w C++23 odpowiedni `std::move_only_function`. Nie zamieniaj własności na `shared_ptr` wyłącznie po to, żeby przypadkowo obejść wymaganie kopiowalności.
